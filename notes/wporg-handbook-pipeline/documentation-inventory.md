# Inventory of WordPress.org documentation sections to consider for standardization

Date: 2026-10-11. Page counts are live `X-WP-Total` values from each site's REST API on that date, except HelpHub,
which comes from `raw/articles.json`. Detail per site is in `research/03-handbook-landscape-survey.md`; the
importer mechanics are in `research/02-wporg-consumer-side.md`.

The end goal is one way of authoring and publishing documentation across wordpress.org, regardless of which
model wins. This note lists every section, how it is published today, and whether it belongs in scope.

## Tier 2: developer-facing, edited in wp-admin. Primary candidates

| Handbook | Pages | Today | Why it is a candidate |
|---|---|---|---|
| Theme handbook, developer.wordpress.org/themes | 139 | `theme-handbook` CPT, `handbook_editor` role, issues in Documentation-Issue-Tracker (`themes` label). **No GitHub repo exists.** | Overlaps heavily with Block Editor content: theme.json reference is duplicated in both (Gutenberg #56499), and block theme docs change with every Gutenberg release. Strongest "docs next to code" case after per-block pages. |
| Plugin handbook, developer.wordpress.org/plugins | 102 | `plugin-handbook` CPT, same role and tracker (`plugins` label). | A stale GitHub mirror, `WordPress/developer-plugins-handbook` (2023-11), still merges PRs that nobody imports (a 2026-09-23 merge is not live). | Common APIs handbook, developer.wordpress.org/apis | 45 | `apis-handbook` CPT, same role and tracker (`APIs` label). | Small; same ownership and tooling as the other two, so it travels with them. |

## Tier 4: different content models. Name as out of scope, with the reason

| Section | Model | Why out of scope for now |
|---|---|---|
| Code Reference, developer.wordpress.org/reference | `wp-parser-*` CPTs generated from core docblocks by a parser, plus hand-written "More information" in WP | Not Markdown-shaped. Silently stopped updating from 6.4 to 6.9.1; a monitoring lesson rather than a migration target. |
| Developer Blog, developer.wordpress.org/news | WordPress `post`, planned in `WordPress/developer-blog-content` issues | Editorial blog; a manifest model fits poorly. |
| Learn WordPress, learn.wordpress.org | Sensei courses, lessons, tutorials | Different information architecture. Once imported lesson plans from GitHub and abandoned it. |
| Make team handbooks, make.wordpress.org/*/handbook (about 17 teams not yet moved) | `handbook` CPT on each P2, edited by team editors | Contributor process docs owned per team. The `handbook` plugin's config-driven importer already works for Hosting, Test and Accessibility, so moving any team is a governance decision, not a technical one. |
| Docs Style Guide, make.wordpress.org/docs/style-guide | `WordPress/WordPress-Documentation-Style-Guide`, hand-edited manifest | Import status unverified. Docs-team owned; could join Tier 1 once verified. |

## Outside wordpress.org proper

Openverse docs (docs.openverse.org), bbPress and BuddyPress codices, and mobile app docs on wordpress.com.
Leave out.

## Recommendation

- **Scope of the standard:** Tiers 1 to 3, about 1,900 pages across 12 handbooks plus HelpHub. Name Tier 4 as
  out of scope explicitly so nobody assumes it was forgotten.
- **Second wave after HelpHub:** Theme, Plugin and Common APIs handbooks. They share the issue tracker, the
  `handbook_editor` role and Docs-team ownership, and the Theme handbook's overlap with Block Editor content is a
  concrete problem the standard would fix.
- **For Tier 1:** converge on one manifest generator with a CI stale-check (the Secure Custom Fields pattern),
  one importer code path, image sideloading (the Playground pattern), and a manifest-driven redirect mechanism.
